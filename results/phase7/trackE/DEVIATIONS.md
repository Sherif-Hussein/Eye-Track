# Deviations and clarifications, Phase 7 Track E

Nothing here changes a definition or reading rule in `PREREG.md`.

1. **PREREG timestamp.** `PREREG.md` says "about 21:40"; the file was in fact saved at 21:28:55 on 2026-11-02 (file modification time). The first real E2 number was computed at 21:33 to 21:38 and the first real E3 number at 21:38, so the file still precedes every real-label computation.
2. **E2, source of the training negatives (clarification, as pre-registered).** The task text pointed to the `oof/*_persons.csv.gz` files, which hold the held-out statistics and the stored `tau_fpr7` but not the training negatives. The training negatives were recovered by calling the Phase 4 person-level code (`edd.unified.persons_mean / persons_cit / persons_chen`) on the stored inner out-of-fold scores in `results/phase4/unified/checkpoints/*.pkl` (no refit; `edd.unified.thresholds` was wrapped to record its inputs, return value unchanged). For every task and every (repeat, fold[, experiment]) the recomputed nominal threshold equals the stored `tau_fpr7` (max abs difference at most 4.4e-16, 790 fold keys in 16 tasks), so the conservative threshold is built on exactly the training negatives behind the nominal one.
3. **E2, intervals.** The unit-level Clopper-Pearson interval treats the repeat-averaged decision of each participant as a binomial count (rounded); this is an approximation. With 3 (Mazza 5) repeats over the same participants the decisions are not independent draws, so the intervals are, if anything, not too wide. The participant-cluster bootstrap interval is stored beside it in the CSV (`*_boot_lo/hi`). When the conservative rule is infeasible the rule flags nobody, so detection = 0 and FPR = 0 are properties of the rule, and the interval shown for them is only the binomial interval for 0 events among the units; the table marks these rows with `folds_feasible = 0`.
4. **E2, Chen.** Two Chen conservative variants are reported: the primary one uses the pooled c1 + c2 null exactly like the stored nominal rule (m about 50, so k* = 0 is feasible), and the sensitivity `conservative_c1only` uses one control comparison per participant (m about 25, infeasible). Because z_c2 = -z_c1 the pooled null counts every participant twice, so the primary Chen conservative row is itself optimistic about its guarantee.
5. **E3, person-AUC definition.** The per-fold person AUC pools the control-1 and control-2 statistics (the Track A2 pre-registered pooling); the control-1-only version is in the CSV. The pooled (repeat-averaged) AUC difference for I2b minus rate rule is +0.110 here and +0.115 in the Phase 3 `results.json`; the Phase 3 value uses its own pooling of the same statistics, and the bootstrap interval reported next to the corrected one is the one computed here (B = 2000, seed 20261302).
6. **E1, smoke run.** A one-round smoke test of the E1 script was run on 2026-11-02 21:42 to 21:49 while about 18 Track B python processes were running; its numbers (written to the scratchpad only, never to this folder) are not used. The real E1 run is documented below.

## E1 real runs (2026-11-03)
7. **Three timing runs, not one.** The real run waited from 21:55 on 2026-11-02 (14 Track B processes, CPU 100%) until Track B finished; the machine check passed at 05:13:29 on 2026-11-03 (0 `phase6_trackB`).
   - **Run 1** (8 rounds, files `run1_*`, `log_e1_run1.txt`): started 05:13 with 2 `phase7_trackD` processes (`phase7_trackD_stats.py`, plus an app `selftest` python) running; Track D was present in the first 4 rounds (system CPU 15 to 32% between rounds) and absent in the last 4. It is a valid run by the pre-registered rule (Track D is allowed, load recorded), but its first half is loaded.
   - **Run 2** (10 rounds instead of 8, files `run2_*`, `log_e1_run2.txt`): started 05:17 with no Track B or Track D processes; system CPU between rounds was 6 to 100% (two samples at 100% in rounds 8 and 9 from a non-project process, not identified), and all absolute times are 1.5 to 2 times slower than the other runs. Probably thermal or background load; kept as a replicate.
   - **Run 3** (10 rounds, the main files `E1_*`, `results_E1.json`, `log_e1_run3.txt`): no Track B or Track D process at start, between rounds or at the end; system CPU between rounds 1 to 13% (one reading of 77.6% in round 3). Used as the primary table because it had the lowest background load. This choice was made after seeing all three runs, on load grounds, not on the factors; the factors agree across the three runs (Shapley rate 4.6 to 5.5, code 7.5 to 8.0, model 1.3 to 1.6).
   - Rounds were 10 instead of the 8 in PREREG for runs 2 and 3 (more rounds because of the visible noise; the procedure is otherwise identical). The three runs are also not pooled.
8. **Equivalence of the code paths.** Original and vectorised code gave identical scores in every cell (max abs diff <= 2.2e-16).
9. **Our 1000 Hz model.** It was fitted on the 64-trial Delmas groups 1 to 3 at 1000 Hz with the Phase 4 `tune_fit` recipe (14 features including microsaccade rate; the 13-feature sensitivity is the `ours13` cells). The published model at 30 Hz is an SVM fitted on the 30 Hz track table (the Phase 4 baseline only had a 1000 Hz SVM), which is the like-for-like model for that cell.
